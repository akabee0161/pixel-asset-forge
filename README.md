# pixel-asset-forge

ゲーム用ドット絵アセットを、テキストグリッドから決定的に生成するリポジトリ。
対象は Ankardo（子供向けゲーム）。

PNG を直接生成せず、1文字＝1ピクセルの文字グリッドを git 管理し、`tools/render.py` が
PNG に変換する。差分が「1行＝1ピクセル行」になって修正箇所が追えること、再生成が
決定的であること、パレット差し替えが一括で効くことがこの方式の理由。

## セットアップ

```sh
python3 -m venv .venv
.venv/bin/pip install -r requirements.txt
```

## 使い方

```sh
.venv/bin/python tools/validate.py       # 構造の検査。異常時は非ゼロ終了
.venv/bin/python tools/check_colors.py   # 隣接色の分離度。助言なので hard failure のみ非ゼロ
.venv/bin/python tools/probe_colors.py   # 2色が区別できるか。色を決める前に使う
.venv/bin/python tools/render.py         # assets/**/*.txt -> build/**/*.png（等倍 + x8）
.venv/bin/python tools/tilemap.py        # tile を並べる。継ぎ目と接続の確認用
.venv/bin/python tools/contact_sheet.py  # 全アセットを1枚に並べる
```

```sh
tools/tilemap.py --repeat river_v --grid 4x4      # 1枚を敷き詰める
tools/tilemap.py --layout layouts/example.txt     # マップを組む
```

各ツールとも、引数にファイルやディレクトリを渡せば対象を絞れる。
`--help` に詳細がある。

ツール自体のテスト:

```sh
.venv/bin/python -m unittest discover -s tests
```

## 構成

```
CLAUDE.md                  作業時の規約（短く保つ）
palette/master.json        色名 -> RGB。色は必ずここ経由で参照する
types/<type>/SPEC.md       寸法・構成要素などの機械的な規約
types/<type>/reference/    合格済みアセット＝お手本。絵柄はここで揃える
assets/<type>/<name>.txt   生成物のソース（これが正）
tools/                     render / validate / check_colors / probe_colors / tilemap / contact_sheet
layouts/                   tilemap.py --layout に渡すマップ
tests/                     tools/ のテストとフィクスチャ
build/                     PNG 出力（git 管理外）
docs/HANDOFF.md            設計の経緯と、確定／未確定の区別
ISSUES.md                  見つかっていて直していない課題
seed/face32.py             リポジトリ化前の原型。分解済みで、もう実行経路にない
```

## ワークフロー

```
types/<type>/SPEC.md と reference/ を読む
  -> assets/<type>/<name>.txt を書く
  -> validate.py -> render.py
  -> build/<type>/<name>_x8.png を目視
  -> tile 型なら tilemap.py で並べて継ぎ目も見る
  -> 修正 or 提出
```

目視の前に機械チェックを挟むのが要点。パレット外の色、行の長さ、寸法、使用色数は
安価に落とせる。ただし**機械チェックは目視の代替にならない**ことが実測で分かっている
（後述）。挟むのは安い異常を先に落とすためであって、目視を減らすためではない。

    - 人の手 `village` `shop` `well` `signpost` `fence_h` `fence_v` `crop_field`

    - レイアウト例は `layouts/field.txt`

石・木・金物・ガラス・花は既存の `stone_*` `wood_*` `metal_*` `water_*` を流用。

見つかっていて直していないものは [`ISSUES.md`](ISSUES.md) にまとめてある。

## `unit` 型

タイル上を動くキャラクターのスプライトシート。
[character-tactics](https://github.com/akabee0161/character-tactics) の
マップスプライトに差し込む前提で、**1体（ロラン）だけ作って仕組みの限界を測った**。
設計の経緯は `docs/2026-09-20-unit-sprite-sheet-spec.md`、手順は同 `-plan.md`。

### 規約

| | |
|---|---|
| 解像度 | 32x32、`bg: transparent`、`# light: upper-left` |
| 構図 | **足元 y=30、左右中央、背丈 24〜26px** |
| 絵柄 | `face` の流儀（全周1pxの輪郭・髪4階調）は**持ち込まない**。全身32pxでは顔が3〜4pxしか取れない |
| 並び | 12行 = 3状態 × 4方向。行 0-3 `idle` / 4-7 `walk` / 8-11 `attack`、各ブロック内は down, up, left, right |
| コマ | `idle` 2 / `walk` 4 / `attack` 3。列数は最大コマ数に揃え、余りは透明 |
| 構成 | `walk` は `[base, walk_a, base, walk_b]`、`attack` は `[atk_wind, atk_hit, base]`。中間と戻りは `base` の流用 |

シート定義は `sheets/<unit>.txt`、コマの本体は `assets/unit/<unit>/`。
`tools/sheet.py sheets/roran.txt` で `build/sheets/roran.png`（128×384）と
`roran_preview.png` が出る。

**定義ファイルを `assets/` の下に置いてはいけない。** `validate.py` と `render.py` は
`assets/` 以下の `*.txt` を全部 `rglob` するので、定義をグリッドとして解釈して落ちる。
`layouts/` がトップレベルにあるのと同じ理由である（この穴は実際に踏んだ）。

### 目視の手順

`tile` の3通りに相当するもの。**1コマの `_x8.png` だけでは終わらない。**

1. `sheet.py` のプレビュー。コマ境界線・**赤い足元ライン(y=30)**・青い中心線が重ねてある。
   アニメで一番出る欠陥は「コマ間で足元や体の中心が1pxずれて絵がガタつく」で、
   1コマの拡大画像を見ても分からない
2. **ゲームに入れて動かす。** 縮小されて初めて分かることがある（下記）

### 収束回数の実測（`unit` 型 / ロラン1体）

手描き18枚・ミラー派生6枚。差し戻しは**自己判断ぶんのみ**を数えた。

| コマ | 差し戻し | 理由 |
|---|---|---|
| `down_base` | 2回 | ①胸当てと盾が同じ金属色で隣接し1つの塊に融合 → 金属を盾と剣だけに限定。②剣が盾と同じ金色かつ刃4pxで小物に見える → 刃を `stone_*` にして長さを倍に |
| `left_base` | **3回** | ①胴幅が正面と同じで横向きに見えない → 14px幅を10px幅に。②頭の輪郭が左右対称で正面顔に見える → 鼻を輪郭の外に1px出す。③顔が3列しかなく髪に埋もれる → 顔を5列に |
| `up_base` / `right_base` | 0回 | |
| `breathe` / `walk` / `attack` | 0回 | 下記のとおり `base` からの差し替えで作った |

**32pxの横顔がいちばん難しい。** 3回描き直してもなお顔は「淡い楔形」にしか読めない。
髪のあるキャラの横顔は32pxでは限界に近い。

### `base` と派生コマの差分は極端に小さい

`left_base`（1024ピクセル）との差分を測った結果。

| コマ | 差分行 | 差分ピクセル |
|---|---|---|
| `left_breathe` | 10行 | 63px |
| `left_walk_a` | 3行 | 15px |
| `left_walk_b` | 3行 | 10px |

`# from:` は**部分差分を持てない**（本体の行を持てず、5種の全体変形しか掛けられない）ため、
1〜6% しか違わないコマを全身グリッドのコピーとして持っている。
**`shift_band` のような部分変形を足せば `breathe` 3枚は丸ごと消える**（呼吸は
「頭部を1px下げて首を1行潰す」だけの純粋な行シフトで、実際にスクリプトで生成した）。
`walk` と `attack` は脚と剣の配置そのものが変わるので、変形では作れない。

### `mirror_x` はキャラにも使えた（ただし光源は反転する）

右向き6枚は `left_*` からの `mirror_x` 派生にした。**並べると胴の明部が左上から右上へ
移るのが見え、盾も反対の腕に移る。** 依頼者の判断で続行。却下していれば手描きは
18枚から24枚に増えていた。

### アンカーチェックは24コマ中4件しか出さず、真陽性は0

`sheet.py` の足元・中心の実測は**助言のみで終了コードに影響させない**。実測結果:

| 段階 | コマ数 | 「off」 | 内訳 |
|---|---|---|---|
| idle まで | 8 | **0件** | |
| 完成時 | 24 | 4件 | 全部 `atk_hit`。剣を前へ振り出すので中心がずれる = **仕様どおりの逸脱** |

**真陽性0・偽陽性0。** このチェックはまだ一度も欠陥を拾っていない。
効いているのはプレビュー画像の赤い足元ラインを目で見ることのほう。
機械チェックの案が実測で空振りするのは、この repo では
[4回目](#深いチェックを試して2回落としている)になる。

### `check_colors.py` が `unit` 型で初めて実際の欠陥を拾った

呼吸コマで頭が1px下がった結果、後頭部の `hair_dark` が肩の `cloth_shadow` と直接接して
**ΔE 7.7（しきい値10）** になった。`up_breathe.txt` だけに出る欠陥で、
`validate.py` は通り、拡大画像でも気付けない。境界に輪郭を1px入れて解消した。

**描く前の `probe_colors.py` も通した。** 将来タイルに乗せる前提なので、地面との分離を先に測った
（`cloth_base`/`grass_base` ΔE 84.4、`cloth_base`/`dirt_base` ΔE 55.2、
`metal_base`/`stone_base` ΔE 63.5）。いずれも十分離れている。

### ゲームに入れて分かったこと

character-tactics の `feat/roran-map-sprite` に差し込み、ヘッドレス Chromium を CDP で
駆動して確認した。

**確認できたもの:** 配置画面での表示、idle の呼吸（頭が1px上下する）、歩行の脚の交互、
**4方向すべて**（down / up / left / right）、`attack` の振りかぶりコマ。

**1. 絵が整数倍で表示されない。** 論理解像度 540×945 に対して canvas の実サイズは
430×753 だった（**0.796倍**）。32px のコマは 25.5px に縮む。
`fitCanvas` は画面に合わせて連続的に拡大率を決めるので、**整数倍になる保証がない。**

**2. その結果、1〜2px の細部は丸ごと消える。** 振りかぶりコマで上げた剣は、
`_x8.png` では肩の横にはっきり見えるのに、**ゲーム内では完全に消えて「剣が無くなった」ように見える。**
32pxで描ける最小の線が、表示側で残るとは限らない。

**3. 論理位置はキャラの腰に来る。** ゲーム側は `center - frame/2` で貼るので、
足元(y=30)は論理位置より14px下に描かれる。HPバー・リング・旗はすべて腰基準になる。

**4. 1体だけ本番絵にすると画面上で浮く。** 残り8体は仮絵のままなので、
絵柄が混ざることは避けられない。

**攻撃の打ち込みコマ（`atk_hit`）はゲーム内で捉えられなかった。**
交戦は確実に起きている（ステージ3で全滅した）が、約300コマ連写しても
打ち込みの姿勢に一致するコマが1つも取れなかった。攻撃は 3コマ / 12fps = 0.25秒しか出ず、
打ち込みはそのうち約83ミリ秒で、さらに 0.796倍で刃が落ちるため、
連写で拾うのが難しい。**未確認として課題に残す。**

### 草原セットの決めごと

**道はどのタイルも四辺の同じ10セル（index 3〜12）を使う。** 直線・曲がり・
十字・T字がこれだけで噛み合う。道の縁の揺らぎは行0・7・8・15には置かない
（隣のタイルが合わせにいく行だから）。

**道に縁取り色は使わない。** 川の均一な1pxの岸が運河に見える原因だったので、
道では不規則な境界そのものに縁の役をさせている。

**川の岸は土2px。** `river_*` `bridge_*` はすべてこの断面（草・土2px・
`water_shadow`・水・`water_shadow`・土2px・草）で端を揃えてある。

**樹冠は `grass_*` で塗らない。** `leaf_hi` の初案は `grass_base` と ΔE 5.9 で、
`check_colors.py` の hard failure だった。地面の緑で木を塗ると地面に沈む。

**地面のテクスチャは全タイルで同じ密度にする。** `grass_flowers` は `plain` の
房の配置をそのまま引き継いで花だけ足し、`dirt` は同じ配置を土の色で置いている。

### 城内マップは壁を2タイルで作る

城の**中**は、フィールドと同じ真上見下ろしの床に、壁だけ正面が見える面を足して作る。

```
wall_top        壁の天面（真上から）
wall_face       その下に置く壁面（正面が見える）
```

南を向いた壁だけがこの2段構成になる。左右の壁は `wall_top` の列だけで、
南側の壁も `wall_top` だけ（面が視点と反対を向くため）。`wall_face` の列
0〜3 と 12〜15 は `wall_face_{window,torch,banner}` と `door_closed` でも
同一にしてあり、壁の並びのどこにでも差し込める。

**角の2枚はミラーで持てない。** `wall_corner_nw` は光を受けて明るく、
`wall_corner_ne` は影に落ちる。変形は光源を一緒に動かすので表現できない。

**床パターンはタイルの行0・列0を基準に置いてある。** そのため
`throne` `pillar` `brazier` `bookshelf` `carpet_end_n` のように床の上に物を
置くタイルは、端の数列に `floor_stone` と同じ行を書いておけば、隣に敷いた床と
目地がそのまま繋がる。

### tile 型は輪郭を回さない

`face` と `item` は「全周に `outline` を1pxで回す」が、`tile` にはこの規約を
適用しない。タイルは隣接して敷き詰めるため、輪郭を回すと常に格子が見える。
`tile` の縁は地続きにし、輪郭は城のような**物体のシルエット**にだけ使う。

### 継ぎ目の機械チェックは作らなかった

「並べて初めて見える欠陥」を機械で拾えるか試した。タイルをトーラスとみなして
巡回的な行・列差分を取り、継ぎ目付近の突出を見る方式。壊れた `river_v` を
`tests/fixtures/river_v_seam_bug.txt` に再現して測った。

| タイル | 継ぎ目付近の突出 |
|---|---|
| **壊れた `river_v`** | **4.0** |
| `castle_se` / `castle_sw`（正常） | 12.0 |
| `river_ne` ほか曲がり（正常） | 8.0 |
| `plain` / `river_v` / `river_h`（正常） | 0.0 以下 |

**分離できなかった。** 城の分割タイルも曲がりも、そもそも自分自身と
敷き詰めるものではないので端で大きく変化するのが正常である。
自己タイリングするタイルに限れば分離できるが、そのためには
「このタイルは自己タイリングする」という宣言をヘッダに足す必要がある。
真陽性1例のために形式を広げる価値はないと判断して**実装しなかった**。
経緯は [`docs/2026-09-19-tiling-tools-spec.md`](docs/2026-09-19-tiling-tools-spec.md)。

代わりに `tilemap.py` が全タイルの 3x3 画像を既定で出す。目視が答えになる。

### ミラーはコピーで持たない

川の曲がり4種のうち3枚は、本体を持たない派生ファイルにした（HANDOFF 2.4）。

```
# from: river_ne.txt
# transform: mirror_x
```

移行時、派生に置き換えた後の PNG が置き換え前と**ピクセル単位で一致する**ことを
確認している。

草原セットで派生は8点に増えた。道は曲がり3種・T字3種・横向きを、川は `river_h` を、
橋は `bridge_v` を派生で持っている。道が全部派生で済むのは**平らな地面には光の向きが
無い**からで、同じ理由で城の壁の角は2枚とも手で描いてある。

`bridge_v` だけは回転の向きに意味がある。デッキの明るい辺は北の行で、
**反時計回り**ならそれが西の列に移って `upper-left` のままになる。時計回りだと
ハイライトが光源の反対側に行く。

なお `tests/fixtures/river_v_seam_bug.txt` の相方は、以前は生きている
`assets/tile/river_v.txt` だった。川の岸を作り直したときに全行が食い違って
テストが落ちたので、当時の正常版を `tests/fixtures/river_v_first_version.txt`
として固定した。**回帰テストが現役のアートを参照していると、アートの更新で落ちる。**

### 収束回数の実測（item 1点目）

**5周。** 各周で直した内容は以下。

| 周 | 直したこと |
|---|---|
| 1 | 蓋が斜めに切り落とした台形で宝箱に見えない。金具帯が柱に見える。錠前が読めない |
| 2 | 蓋の肩を丸め、金具帯を外側へ出して蓋と本体を縦に貫かせ、錠前を4x3に拡大 |
| 3 | 左帯が `metal_hi` べた塗りで右帯と別素材に見える。境界線が黒帯。底が潰れている |
| 4 | 帯を `metal_base` に統一、境界線と底の明度を上げる |
| 5 | 左端1px列のハイライトが面の照りでなく縁の光に見える。帯の右側の面へ移動 |

内訳としては、1〜2周目がシルエットと構成要素の配置、3〜5周目が明度配分。
機械チェックで落ちた回数は0で、5周はすべて目視由来。

| アセット | 周 | 内訳 |

| 城（2x2） | 4 | 胸壁が読めない → 塔と壁の分離 → 目地と金具が埋もれる → アーチと窓 |
| 川（6点） | 2 | **縦に繋がらない継ぎ目バグ**（後述）→ 収束 |
| 橋 | 3 | デッキが全幅に伸びて草地で途切れる → 黒枠に挟まれて木に見えない → 収束 |
| 城内（20点） | 2 | 階段が段でなく縞に見える／`floor_worn` のひびが床のゴミに見える → 収束 |
| 草原（27点） | 3 | 草の反復が格子に見える（3案を実測）／`forest` が緑の紙吹雪・川の岸が細すぎる → 切り株・井戸・道標が別の物に見える |

城の4周はすべて「要素が読めるか」の問題で、明度配分の調整は1回も発生していない。
宝箱（5周中3周が明度配分）とは内訳が逆になった。**構成要素が多いアセットほど
配置の周回が増え、単純なアセットほど明度の周回が増える**という傾向が出ているが、
2サンプルなので断定はできない。

城内セットの2周は、20点を1周目でまとめて書き、2周目で上の2件だけを直した。
1点ずつ収束させた宝箱や城と違い、床・壁・絨毯という共通の下地を先に決めたので、
個々のタイルではなく**セット全体で2周**という数え方になっている。

**`validate.py` が初めて異常を検出した（城内セット、7ファイル）。** ただし
絵の誤りではなく形式の誤りで、コメント行に書いたコロンが「ヘッダの書き損じ」として
落ちた（`# A runner down a hall: ...`）。目視より前に、レンダリングすらされずに
止まる種類の誤りである。

絵の側では、機械チェックで落ちた回数はここでも0のまま。**65点あるタイルを通して、
`validate.py` が「絵として」の異常を検出したことは一度もない。** 往復回数を
削っているという HANDOFF 2.2 の前提は、形式エラーについては裏付けが取れたが、
絵については依然として取れていない。

草原セットでも `validate.py` が落としたのは行長の数え違いだけで、これは十数回出た。
16文字を手で数える作業に対しては明確に効いている。

### 草地の反復は3案を実測した（草原で判明）

`plain` は「敷き詰めると房が格子に整列する」という理由で作り直した。
案を3つ作って、4x4 に並べた絵を毎回見比べている。

| 案 | 並べた見え方 |
|---|---|
| 16px周期・疎な2px房（初版） | **格子。** 同じ位置の房が縦横に整列して壁紙になる |
| 8px周期・4マークの反復 | **織物。** 格子ではなくなるが、規則的な織り目に見える |
| 不均一な間隔・形を混ぜる・端をまたぐ房（採用） | テクスチャとして読める |

効いたのは周期を変えることではなく、**マークの形を揃えないこと**と、
**タイルの左右端に半分ずつ置いた房**（並べて初めて1つに繋がる）だった。
周期そのものは16pxのままである。

1枚のタイルを敷き詰める以上、周期は消せない。消せるのは**周期が目に留まること**
だけで、これは `_x8.png` を1枚見ても判定できない。`tilemap.py --repeat` が要る。

### マップに置いて初めて「別の物」に見える

川の継ぎ目バグは並べて初めて見えるものだった。草原セットでは、それとは別の
「並べて初めて見える」欠陥が出た。**1枚では何だか分かるのに、マップに置くと
別の物に見える**というものである。

| タイル | `_x8.png` では | `layouts/field.txt` に置くと |
|---|---|---|
| `stump` | 年輪のある切り株 | 木箱 |
| `well` | 井戸の石枠と桶の棒 | 手提げの桶 |
| `signpost` | 板の付いた柱 | 台またはキノコ |

拡大して1枚だけ見るときは、こちらが何を描いたか知っているので、そう見えてしまう。
周りに他のアセットが並ぶと、その先入観が効かなくなる。**目視の締めは必ず
`--layout` で組んだマップにすること。**

### 1枚で見ても分からない欠陥がある（川で判明）

川の初版は、**1枚で見る限り完璧だったが、縦に並べると境界に暗い横帯が出た。**
水の陰影を「バンクに接するセルは暗くする」で決めていたところ、タイルの外を
一律「水ではない」と扱っていたため、上端と下端の水が岸として暗くなっていた。

このバグは `validate.py` も `check_colors.py` も通過する。`build/*_x8.png` を
1枚ずつ目視しても見つからない。**同じタイルを並べて初めて見える。**

`tile` 型では、1枚の目視だけでは検証が完了しない。`tools/tilemap.py` で並べて
継ぎ目を確認すること。このツールはこのバグがきっかけで作った。

### 機械チェックと目視は代替関係ではない

上の結果を受けて、[pixellint](https://github.com/Li-Mingshuang/pixellint) の
**隣接色の分離度チェック**を `tools/check_colors.py` として取り入れ、効果を実測した。
仕様と経緯は [`docs/2026-09-19-color-separation-spec.md`](docs/2026-09-19-color-separation-spec.md)。

| | 結果 |
|---|---|
| 目視が見つけた11件のうち、このチェックが拾えたもの | **0件** |
| 目視が5アセット分見逃していた欠陥のうち、このチェックが拾ったもの | **1件** |

拾えたのは `types/face/reference/knight.txt` の `outline` と `pupil` が
**同じ `#1a1228` で、瞳孔が目の輪郭に同化している**こと。何度も目視して
気付かなかった。逆に目視が見つけた「目地が消えた」「塔が壁と分離していない」は
*同じ色*が隣り合っていたケースで、色ペアが発生しないため原理的に検出できない。

**機械は「同じ色に別の名前が付いている」を見つけ、目は構図を見つける。**
深いチェックを足しても目視の周回は減らない、というのが現時点の結論。

pixellint 本来のしきい値（ΔE 22）をそのまま使うと、階調の隣り合いが全部警告に
なった。同リポジトリ自身が「厳しすぎるチェッカーは拾う以上のコストを払う」と
記録しており、その罠に即座に踏んだ。収束済みアセットが無警告になる ΔE 10 まで下げてある。

**色を足すときは、描く前にしきい値へ当てにいくと速い。** 城内セットで10色を
足したときは、実際に隣り合わせる予定の約100ペアを先に測り、`has_lightness_edge` か
ΔE のどちらかを確実に超えるように色を決めてから描いた。結果として20点すべてが
警告0で通っている。これは `check_colors.py` が有能だったという話ではなく、
**このチェックは描く前に使うと設計の道具になり、描いた後に使うと（実測どおり）
ほとんど何も拾わない**ということである。

この測定は `tools/probe_colors.py` にしてある。城内セットと草原セットで2回とも
書き捨てにしていたが、毎回違っていたのは**測るペアの一覧だけ**で、計算は2回とも
`check_colors.py` から import していた。ペアの一覧は引数で渡せるものなので、
書き捨てにする理由が無かった。

**草原セットで、この使い方が初めて色を却下した。** 樹冠用に置いた
`leaf_hi = #3f8a3c` は `grass_base` と **ΔE 5.9 で hard failure** だった。
木の緑を地面の緑からそのまま持ってくると、木が地面に沈む。候補を7色測って、
地面の3色すべてに対して ΔE 17 以上を確保できる `#2e8055`（やや青寄りの緑）に
した。描いてから気付いていれば、木・針葉樹・森の3点を描き直していた。

| 候補 | 地面の緑との最小 ΔE | |
|---|---|---|
| `#3f8a3c` | 5.9 | hard failure |
| `#37803f` | 9.7 | 警告 |
| `#2f7a4a` | 13.4 | 可 |
| `#2e8055` | **17.4** | 採用 |

この表は再現できる。

```sh
tools/probe_colors.py --candidate '#3f8a3c' --against grass_base grass_hi grass_shadow
```

### 深いチェックを試して2回落としている

機械チェックを増やす試みは、いまのところ2件とも実測で不採用になっている。

| 試したもの | 結果 |
|---|---|
| 孤立ピクセル検査（周囲すべてと大きく異なる1pxを検出） | **斜めの輪郭を全部検出した。** 斜めの輪郭ピクセルは定義上4近傍すべてと色が違う。概念から誤り |
| 継ぎ目チェック（トーラス巡回行差分） | **正常なタイルと分離できなかった**（上表） |

採用した `check_colors.py` も、pixellint 本来のしきい値（ΔE 22）では階調が全部
警告になり、ΔE 10 まで下げることになった。

つまり**機械チェックの案は3回とも、実測して初めて撤回か下方修正になっている**
（撤回2件・しきい値の下方修正1件）。**新しいチェックを思いついたら、実装して
既存アセット全件に掛けて偽陽性を数えること。**

### 先行例と、乗り換えなかった判断（2026-09-19 調査）

この「文字グリッドを正として PNG を生成する」設計に独自性はない。
`XPM`（X PixMap, 1989）が「文字グリッド＋文字→色マップ」そのもので、
2026年に入ってからも複数の個人が独立に同じ形に到達している。

| | ★ | 概要 |
|---|---|---|
| [pixellint](https://github.com/Li-Mingshuang/pixellint) | 0 | 文字グリッド＋固定パレット。検証が深い。本リポジトリの `check_colors.py` の出典 |
| [godot-pixel-studio](https://github.com/khalil852/godot-pixel-studio) | 0 | `legend:` + `grid:` のほぼ同一設計。Godot 向け |
| [PixTXT](https://github.com/Fantety/PixTXT) | 3 | グリッド形式の仕様化。RLE・アニメ・スプライトシート・GIF 出力付き |
| [drawstic](https://github.com/TorbenKoehn/drawstic) | 0 | グリッドでなく描画コマンドの DSL |
| [yoyopixel](https://github.com/SbName/yoyopixel) | 5 | テキストのみの LLM に描かせる。Claude Code skill / MCP 対応 |

**依存できる成熟度のものは1つもない**（全て0〜5スター、単独作者、数週間〜数ヶ月）。
そのため自前実装を維持する。

**PixTXT には乗り換えない。** パレットをファイル内に持つ設計で、
HANDOFF 2.3「プロジェクト全体でマスターパレットを持つ」と逆行する。
RLE は16x16では無意味で、アニメ・シート機能は現時点で使わない。
アニメーションやスプライトシートが必要になった時点で再検討する。

### 手書きグリッドは約32pxで限界が来る（知見）

[pixellint](https://github.com/Li-Mingshuang/pixellint) と
[godot-pixel-studio](https://github.com/khalil852/godot-pixel-studio) が独立に
「32px を超えると手書きグリッドは読めなくなる（64×64 は4096個の判断）」と書いている。
**規約にはしていない**が、本リポジトリでも整合する挙動が出た。

16x16 の宝箱は16行を直接書いたのに対し、32x32 の城は直接書けず、
`L_BODY = "otnnnmo"` のように名前を付けた部品を組んで行を作っている。
32x32 の時点で既に直接記述が破綻していたことになる。

## 確定していること / していないこと

大元の整理は `docs/HANDOFF.md` の 3 節にある。ただしあれは作成時点のログなので、
現在の状態はこちらを見ること。

| | |
|---|---|
| **確定** | 解像度 `face` = 32x32、`item` = 16x16、`tile` = 16x16、`unit` = 32x32 |
| **確定** | `tile` はシームレス。全周に輪郭を回さない |
| **確定** | `unit` は足元 y=30・左右中央・背丈24〜26px。シート定義は `sheets/` に置く（`assets/` 不可） |
| **未確定** | 目指す絵柄（「SFC世代相当」以上の指定はない） |
| **未確定** | アセットあたりの色数上限。`# max_colors:` は実装済みだがどのアセットでも未使用 |
| **未確定** | マスターパレットの具体的な色 |
| **未確定** | `face` / `item` / `tile` / `unit` 以外の型と、その解像度 |
| **未確定** | `unit` で許す最小の線幅（0.796倍表示で1pxの刃が消えた。[上記](#ゲームに入れて分かったこと)） |
| **未確定** | `tile` をゲームへどう渡すか（1枚ずつの PNG / タイルセット / マップの完成品）。`tilemap.py` は検証用 |

勝手に確定させないこと。
